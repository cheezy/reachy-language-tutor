# Stride Configuration

Hooks run on this machine at four points in a task's life. Each line below runs as its own
command, in order, from the repository root. A **blocking** hook stops the workflow if any
line exits non-zero.

Every command names the Python interpreter explicitly rather than relying on an activated
virtualenv, which is the same convention as `docs/SETUP.md`. **If your virtualenv is not at
`~/dev/reachy/reachy_mini_env`, change these paths.**

## before_doing

Executes before starting work on a task (blocking, 60s timeout).

```bash
echo "Starting $TASK_IDENTIFIER: $TASK_TITLE"
git status --short
$HOME/dev/reachy/reachy_mini_env/bin/python -c "import reachy_language_tutor; print('app imports OK')"
```

The import check is the cheap version of "is my environment still sane" — it catches a broken
or half-upgraded virtualenv now, rather than after you have written code against it.

There is deliberately **no `git pull`** here, and that stays true now that the repository has
a remote (`origin`, with `main` tracking `origin/main`). The original reason was that a pull
would fail without one; the reason now is different, and worth writing down so nobody restores
it as an oversight. This repository has a single writer, so a pull can only ever be a no-op —
while `git pull` against a worktree with uncommitted changes fails outright, which would block
the claim of every task started mid-edit. A blocking hook that can only lose is not worth its
round trip. Add it back the day a second machine or a collaborator starts pushing.

## after_doing

Executes after completing work (blocking, 120s timeout).
If this fails, task completion should fail.

```bash
$HOME/dev/reachy/reachy_mini_env/bin/ruff format --check reachy_language_tutor/src
$HOME/dev/reachy/reachy_mini_env/bin/ruff check reachy_language_tutor/src
STRIDE_TEST_FLOOR=enforce $HOME/dev/reachy/reachy_mini_env/bin/python -m pytest reachy_language_tutor -q
$HOME/dev/reachy/reachy_mini_env/bin/python scripts/check_test_floor.py
```

This is the real quality gate. In order:

1. **`ruff format --check`** — fails if any file is not formatted to the project's style. It
   only reports; run the same command without `--check` to actually reformat.
2. **`ruff check`** — the linter. Catches unused imports, undefined names, and similar.
3. **`pytest`** — the test suite; every test must pass. It is **not** quick: measured at
   77s on 2026-09-24, against this hook's 120s timeout, with the three slowest tests at about
   5s each (deferred-checkpoint erasure tests) and a run of face-enrolment tests at about 3s
   each. Check the headroom when adding slow tests; `pytest --durations=12` shows where it goes.

Both tools are already configured in `reachy_language_tutor/pyproject.toml` and are installed
with `pip install pytest pytest-asyncio "ruff==0.15.20"`.

> **Why the suite reports skips.** Seven files come from the upstream conversation app and test
> profile *switching*, which this app disables by setting `config.LOCKED_PROFILE`, so 30 of
> their tests cannot pass here. They are skipped individually, by a `skipif` bound to that
> constant (`reachy_language_tutor/tests/profile_lock.py`), so they start running again by
> themselves if the app ever stops locking its profile. **Nothing else is marked, and
> nothing else is failing.** A Windows wheel path-length test used to pin one packaged path
> as over budget; D23 found that budget was miscounted by 7 characters and the path had been
> inside it all along, so the pin is gone and the test passes on its own merits.
>
> **The collection floor, and why the number lives here.** The line below is the one
> authoritative record of how many tests a full collection must find. It is a MINIMUM:
> removing a test deliberately means lowering it in the same change -- which is the
> point, because the failure being prevented is a *silent* drop rather than a deliberate
> one.
>
> **Adding tests cannot fail this floor, but it CAN fail the bypass guard beside it, and
> D37 is how we found that out.** `test_an_exclusion_on_the_command_line_makes_the_run_fail`
> proves the floor still bites by excluding `test_rpc_control_surface.py` and requiring the
> remainder to land BELOW this number. With that file holding N tests, the floor has to sit
> inside `[collected - (N - 1), collected]`: too low and the exclusion clears it and the
> guard stops firing. D37: the suite grew to 1960, the remainder landed exactly ON the old
> 1922, and that test failed rather than the floor doing its job; raised 1922 -> 1960.
> 2026-09-24 review: raised 1960 -> 2139, the real count, measured with
> `pytest reachy_language_tutor --collect-only -q`. The excluded file now holds **56**
> tests (it held 38 at D37), so the runway is 56: it will need raising again at **2195**
> collected, when `collected - 56` reaches 2139. Set it to the real count when you do,
> and re-measure N while you are there -- both numbers moved in the same change last time.
> A floor drifting below the suite has quietly stopped meaning anything.
>
> <!-- MINIMUM_COLLECTED_TESTS: 2139 -->
>
> It is enforced twice, and the two halves catch different things. `check_test_floor.py`
> above runs its own full collection from outside the suite, so it still works if the
> guard file inside the suite is excluded. `conftest.py`'s session hook reads the count
> of the invocation that is ACTUALLY running, which is the only place a `--ignore` on
> this very pytest line can be seen -- measured before D27: adding
> `--ignore-glob='*test_rpc_control_surface.py'` dropped 38 tests, reported green, and
> the in-suite guard passed inside that run.
>
> These used to be whole-file exclusions in `[tool.pytest.ini_options]`. That also discarded
> 69 passing tests and, worse, meant a test *added* to one of those files was never collected
> and never ran. D21 removed them. Do not put a file-level exclusion back: mark the failing
> test instead. `tests/test_pytest_configuration.py` asserts every test file on disk is
> collected, and will fail if one goes missing again.

## before_review

Executes when task enters review (blocking, 60s timeout).
If this fails, task completion should fail.

```bash
echo "$TASK_IDENTIFIER ready for review: $TASK_TITLE"
git status --short
```

No pull request is created. The remote exists now (see `after_goal`), but this repository has
a single writer committing to `main` and publishing a goal's work with one push when the goal
completes, so a PR per task would have no reviewer to go to. This is where `gh pr create`
belongs if that changes.

## after_review

Executes after review approval (blocking, 60s timeout).
If this fails, mark_reviewed should fail.

```bash
echo "$TASK_IDENTIFIER approved: $TASK_TITLE"
```

Nothing to deploy. The app is published to Hugging Face manually with the app assistant, and
that is not something to trigger automatically on every approved task.

## after_goal

Executes when a goal's final child task completes (blocking, 60s timeout).

```bash
echo "Goal complete: $TASK_TITLE"
git status --short
git push origin main
```

The canonical job for this hook is publishing the goal's work to the remote — the Stride
server flips the goal to Done but never publishes anything itself, so without the push a goal
reaches Done with its work never leaving this machine. That was the state until the remote
existed; it now does, at `https://github.com/cheezy/reachy-language-tutor.git`, with `main`
tracking `origin/main`, so the push is a plain fast-forward.

`git push` is the **last** line deliberately. The `git status --short` above it runs first, so
a goal that finishes with uncommitted work leaves that visible in the hook output, rather than
having it quietly left behind by a push that only ever sends commits.

Blocking is the behaviour to want here: a goal whose work did not reach the remote should not
be recorded as finished. The orchestrator's own check afterwards is
`git log origin/main..main --oneline`, and an empty result means the push landed.
